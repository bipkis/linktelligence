# GNN Experiments

Experimental scripts and evaluation results for the Linktelligence network-topology GNN.

This directory contains reproducible synthetic dataset generation, model evaluation, stress testing, and v2/v3 comparison scripts.

## 1. Experimental objective

The goal is to evaluate a graph neural network that predicts three graph-level targets:

| Head | Task | Target |
|---|---|---|
| `score` | Regression | Topology quality score in `[0, 1]` |
| `bottleneck` | Binary classification | Whether a bottleneck is present |
| `security_flaw` | 3-class classification | Number of distinct security issue categories: `0`, `1`, or `2` |

The model is trained on synthetic LAN topologies. Labels are generated by deterministic rules in `heuristics.py`.

**Important:** The experiments evaluate the ability to reproduce these labeling rules on previously unseen synthetic graphs. They do not establish accuracy on real enterprise networks.

## 2. Model architecture

Both v2 and v3 use the same `NetworkGNN` architecture. The improvement from v2 to v3 comes primarily from the training data distribution, not from changing the network architecture.

### Graph features

Each node has 12 input features:

- 7 node-type one-hot features;
- normalized node degree;
- normalized sum of incident bandwidth;
- normalized sum of incident throughput;
- critical-node indicator (`router` or `firewall`);
- throughput-to-bandwidth ratio.

Each edge has 2 features:

- normalized bandwidth;
- normalized throughput.

Edges are represented in both directions.

### GNN

The model uses two edge-aware `GATConv` layers:

- hidden dimension: 64;
- attention heads: 4;
- edge feature dimension: 2;
- ReLU activations.

Graph-level pooling differs between prediction heads:

- `score`: global mean pooling;
- `security_flaw`: global mean pooling;
- `bottleneck`: global max pooling.

The bottleneck head uses max pooling to preserve strong node-level signals that could be diluted by averaging.

## 3. Synthetic labels

The source of truth for labels is `heuristics.py`.

### Bottleneck

A bottleneck is present if at least one critical node (`router` or `firewall`) has total incident throughput greater than total incident bandwidth.

The score penalty is applied once per category, regardless of the number of overloaded nodes.

### Security issue A: unprotected hosts

Issue A is present if:

- at least one host exists;
- no firewall exists in the topology;
- no IDS/IPS device exists in the topology.

### Security issue B: direct printer-router connection

Issue B is present if at least one direct edge connects a printer and a router.

The security target counts distinct categories:

| Issue A | Issue B | `security_flaw` |
|---|---|---:|
| No | No | 0 |
| No | Yes | 1 |
| Yes | No | 1 |
| Yes | Yes | 2 |

The score starts at `1.0` and applies the following category penalties:

| Category | Penalty |
|---|---:|
| Bottleneck | 0.3 |
| Unprotected hosts | 0.4 |
| Printer-router connection | 0.2 |

The score is clamped to `[0, 1]`.

These rules are used for training-label generation only. Runtime inference in `server.py` uses GNN predictions and does not invoke heuristic analysis.

## 4. Dataset versions

### v2: original generator

The original dataset contains 2,000 connected synthetic graphs:

- 5–19 nodes per graph;
- node types sampled using fixed weighted probabilities;
- bandwidth and throughput sampled from configured ranges;
- labels generated by `calculate_labels()`.

The original generator does not explicitly balance security scenarios. Consequently, the distribution of security labels changes substantially when graph size increases.

During dataset auditing, 30 historical score labels were found to disagree with the current heuristic implementation. All 30 cases contained exactly two overloaded critical nodes. Their scores were updated to apply the bottleneck penalty once per category.

The corrected dataset contains zero label mismatches against the current `calculate_labels()` implementation.

### v3: balanced multi-size dataset

The v3 dataset contains 2,000 graphs, divided into four size ranges:

| Size range | Samples |
|---|---:|
| 5–19 nodes | 500 |
| 20–39 nodes | 500 |
| 40–59 nodes | 500 |
| 60–100 nodes | 500 |

Each size range contains four controlled security scenarios:

| Issue A | Issue B | Samples per size range |
|---|---|---:|
| No | No | 125 |
| No | Yes | 125 |
| Yes | No | 125 |
| Yes | Yes | 125 |

Overall security class distribution:

| Class | Samples | Share |
|---|---:|---:|
| 0 | 500 | 25% |
| 1 | 1,000 | 50% |
| 2 | 500 | 25% |

The generator uses seed `3030`.

The scenario generator deliberately modifies node types to ensure that each requested security combination is present. Therefore, v3 is a controlled experimental dataset, not a representation of natural incident prevalence.

## 5. Train / validation / test split

The training pipeline uses a deterministic two-stage stratified split:

- Train: 70%;
- Validation: 15%;
- Test: 15%.

Stratification is performed on the joint classification target:

`(bottleneck, security_flaw)`

The split uses the configured seed for the first stage and `seed + 1` for the second stage.

Validation loss controls checkpoint selection and early stopping. The test split is used only for final evaluation.

The split is not explicitly stratified by graph-size bucket. The observed v3 split nevertheless contains examples from all four size ranges in each subset.

## 7. Independent v3 holdout

A separate dataset of 2,000 graphs was generated with seed `4040`.

It uses the same four size ranges and the same controlled security scenarios as v3 training, but contains newly generated graph structures.

The model was not trained on these holdout graphs.

### Results by graph size

| Nodes | Score MAE | Score RMSE | Bottleneck macro-F1 | Security macro-F1 |
|---|---:|---:|---:|---:|
| 5–19 | 0.0452 | 0.0667 | 0.9585 | 0.9780 |
| 20–39 | 0.0487 | 0.0701 | 0.9818 | 0.9802 |
| 40–59 | 0.0508 | 0.0734 | 0.9478 | 0.9861 |
| 60–100 | 0.0646 | 0.0933 | 0.9620 | 0.9901 |

These results demonstrate generalization to new synthetic graphs from the same controlled generation process. They do not constitute independent validation against real network incidents or expert labels.

## 8. Comparison against the original generator distribution

A separate stress dataset was generated using the original, naturally weighted node-type generator with seed `2028`.

It contains 2,000 graphs with 20–100 nodes.

This dataset has a substantially different security-label distribution:

- Issue A becomes very rare as graph size increases.
- Issue B becomes increasingly common.
- Security class 2 is absent from the larger graph-size groups.

### v2 vs v3

| Size | Model | Score MAE | Bottleneck macro-F1 | Security macro-F1* |
|---|---|---:|---:|---:|
| 20–39 | v2 | 0.0695 | 0.9281 | 0.9512 |
| 20–39 | v3 | 0.0604 | 0.9499 | 0.8086 |
| 40–59 | v2 | 0.0994 | 0.9269 | 0.7797 |
| 40–59 | v3 | 0.0725 | 0.9294 | 0.8040 |
| 60–79 | v2 | 0.1300 | 0.8904 | 0.6094 |
| 60–79 | v3 | 0.0807 | 0.9339 | 0.6383 |
| 80–100 | v2 | 0.1584 | 0.8747 | 0.5656 |
| 80–100 | v3 | 0.0960 | 0.9108 | 0.6041 |

\* Security macro-F1 is calculated over classes observed in the ground-truth subset. It excludes classes absent from the ground truth, so predicted-only classes may not be penalized by this metric. Confusion matrices should be consulted for a complete error analysis.

The v3 model improves score regression and bottleneck classification across all tested size ranges. Security classification on the original distribution remains more challenging, especially for small graphs where the rare class 2 is sparsely represented.

## 9. Experiment scripts

Run commands from the `gnn_prototype` directory.

| Script | Purpose |
|---|---|
| `generate_balanced_data.py` | Generate the controlled v3 training dataset |
| `balanced_holdout_test.py` | Generate and evaluate an independent balanced holdout |
| `holdout_original_distribution.py` | Evaluate v2 on new graphs from the original generator |
| `stress_test.py` | Evaluate performance on larger graphs from the original generator |
| `stress_diagnostics.py` | Inspect security confusion matrices by graph size |
| `stress_label_diagnostics.py` | Inspect security issue prevalence by graph size |
| `compare_v2_v3.py` | Compare v2 and v3 on the same stress dataset |

The scripts currently use some hardcoded checkpoint and temporary dataset paths. Update those constants when running the historical comparisons on another machine. The generators print the temporary dataset directory they create.

The main training pipeline remains in `train.py`.

## 11. Limitations and next steps

Current evidence is limited to synthetic graphs and deterministic synthetic labels.

The evaluation does not establish:

- accuracy on real enterprise LAN topologies;
- correctness of the heuristic rules as a model of real security posture;
- calibration of predicted probabilities under real-world class prevalence;
- localization of problematic nodes or edges;
- robustness to device types, traffic patterns, or graph structures absent from the generator.

Recommended next steps:

1. Make experiment paths configurable through CLI arguments.
2. Add probability calibration using a validation set with a realistic class distribution.
3. Evaluate on independently collected, expert-reviewed network topologies.
4. Investigate node/edge-level localization as a separate modeling task.
5. Keep runtime inference GNN-only; heuristic logic remains a training-label generator.
